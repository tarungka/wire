# WIP-07 runtime RPC contract

This is the executable contract for the current runtime. The original proposal in README.md describes the starting design; this document resolves its differences with WIP-02 (task lifecycle), WIP-05/06 (checkpoints), and WIP-21 (command push). Go request/response structures and codec tags in `internal/rpc/messages.go`, `checkpoint_replication.go`, and `checkpoint_fetch.go` are the wire schema. There is no protobuf/gRPC wire endpoint.

## Connection and framing

Workers initiate TCP/Yamux connections to the coordinator. Both ends accept RPC streams on that connection: the coordinator serves registration, status, heartbeat, checkpoint ACK/authorization and WatchCommands; the worker serves reservation, deployment and checkpoint-trigger RPCs. A method sent in the wrong direction has no registered handler and receives UNKNOWN_METHOD. Each unary request owns one bidirectional stream, carries one request frame, receives one response frame and closes. A caller keeps the stream open until the response; closing it cancels server work. WatchCommands and checkpoint archive transfers retain their existing streaming lifecycles.

The frame is big-endian `length:u32 | method:u16 | request_id:u48 | msgpack payload`. Length excludes its own four bytes and includes the eight-byte method/ID header. Maximum payload is 16 MiB by default. Incomplete, undersized or oversized frames close only their stream; the session remains usable. Success echoes method and request ID; errors use method 0x00ff with the same request ID. Clients reject mismatched method/ID before decoding either success or error. Each client allocates IDs independently; concurrent streams can arrive out of order. A session-wide request-ID high-water mark is **not** a replay filter: it would discard valid concurrent calls. Epoch, deployment attempt and checkpoint identities fence mutations instead.

A 30-second setup deadline bounds streams that do not finish sending a frame. Unary handlers then receive a method-specific context deadline; peer stream closure also cancels that context. Handlers must cooperate with context cancellation. The server cannot forcibly stop arbitrary Go/user code. Streaming handlers clear the setup deadline and use their own cancellation/transfer policy. Session shutdown cancels handlers, closes streams, and waits for them; independent sessions are tracked separately. Handler panics produce INTERNAL_ERROR correlated to the request.

## Methods and errors

All message field names below refer to the Go schema, whose `codec` tags define the actual compact msgpack keys. Responses containing `Accepted=false` are application refusals, not successful mutations and not automatic retry requests. Every method can return SERIALIZATION_ERROR for malformed msgpack, UNKNOWN_METHOD on the wrong endpoint, INTERNAL_ERROR for handler/storage failure and a transport timeout/close error without a response.

## Reservation and deployment lifecycle

1. The scheduler chooses live workers and creates a unique attempt ID. Workers advertising SupportsReservations must have a reverse RPC client bound to their current registration session/epoch. No fallback to unreserved command admission is allowed when such a peer is disconnected.
2. The scheduler obtains all worker leases before publishing deployment. Each reservation uses the attempt ID as its stable ID, belongs to one job and epoch, and defaults to 30 seconds. Capacity is all-or-nothing for each request. A duplicate identical request returns the original lease without extending expiry or reserving more slots. Query and release are idempotent. Expired capacity becomes available on the next query/admission/heartbeat; no absent coordinator is needed to reclaim it.
3. If any worker refuses, partial leases are released (expiry is the fallback after a lost release). Before publishing, the scheduler rechecks leader state, worker/session/epoch and availability. A heartbeat already counting this lease must not make it count twice.
4. Assignments, recovery grants and DEPLOYING are durably written before SubmitJob. A worker validates the entire task list, atomically consumes the lease and installs all task handles, then starts execution. Accepted means admitted, not RUNNING. State restore and operator initialization still precede RUNNING. Failures there arrive as fenced task-status reports.
5. A deployment receipt binds an attempt to the exact request content. Identical retries return success even after all tasks finish; changed content is refused. Receipts and cancellation tombstones live for the coordinator session. Reconnection joins old tasks and discards session-local leases/receipts; the new scheduler uses a new attempt. The random attempt identity is never treated as an ordered counter.
6. An uncertain/failed deployment reply puts the job in FAILING and sends attempt-fenced cancellation. Cancellation of an absent task acknowledges Canceled and records a tombstone, so a late SubmitJob cannot start it afterward. Recovery waits for terminal reports before replacing the attempt. Successful leases have been consumed; unused leases are released/expire.

Older workers omit SupportsReservations and retain WIP-21 DeployTask/checkpoint commands. This mixed-version path is explicitly legacy capacity accounting. Upgraded workers always use authoritative reservations with an upgraded coordinator. Older coordinators ignore the additional registration field and continue to use their command path. Reservations improve safety without requiring a simultaneous cluster upgrade.

## Retry and idempotency

UpdateTaskStatus and AcknowledgeCheckpoint use at most three retries after the first attempt. Retryable server envelopes follow the existing error registry. Ambiguous transport failures retry only operations with safe identity: fenced status, checkpoint ACK/trigger, heartbeat, and reserved deployment/reservation requests. Registration is not automatically retried on another session. The scheduler allows one deployment retry; an uncertain outcome after its budget triggers cancellation rather than starting a second execution.

Backoff starts at 100ms, doubles up to 5s, and uses ±25% jitter. Server retry hints are bounded to 5s before jitter. A caller deadline/cancellation bounds the whole retry loop. Each attempt uses a fresh stream and request ID but retains operation identity. Without a caller deadline, each unary attempt receives its method budget. No transport error implies that the remote mutation was rolled back.

Checkpoint triggers are deduplicated by checkpoint ID under the source queue lock. Duplicate ACKs are validated against the same task inventory and reuse the existing completion decision; commit notification may be resent safely. Completed/aborted decisions are not reversed. Terminal status is monotonic within an assignment, so a delayed retry cannot resurrect a failed attempt. WIP-06's invalidation refund remains idempotent and persisted independently of duplicate RPC delivery.

## Heartbeats and failure handling

The runtime heartbeat interval is 5s, request timeout 2s, and contact loss occurs after six consecutive failures; workers then cancel/join old tasks and reconnect. Coordinator placement and recovery use the configured WorkerTimeout (30s by default), not the obsolete unconditional 15s claim in the original proposal. WIP-08 owns the complete health-policy configuration and SUSPECT/DEAD presentation; the reusable HeartbeatTracker has separate suspect/dead thresholds. Coordinator lost-worker detection already fails affected tasks and enters checkpoint recovery.

WIP-21 WatchCommands is the primary low-latency cancellation/commit/abort path. Heartbeat responses drain the fallback queue. Commands preserve epoch/attempt/checkpoint fencing whichever delivery path is used. A partition does not grant permanent authority to keep old tasks running; reconnect joins them before registering the new session.

## TLS and identity

`node_tls.cert`, `node_tls.key`, `node_tls.ca_cert`, `node_tls.verify_client` and `node_tls.verify_server_name` (and their existing CLI flags) now configure coordinator-worker RPC connections. The coordinator requires its certificate/key when TLS is configured. Use verify_client=true and a CA to require authenticated workers. Workers present their certificate/key, trust the configured CA, and verify the coordinator hostname (or verify_server_name override). TLS minimum is 1.3; invalid configuration fails startup rather than silently using plaintext.

For verified client certificates, every worker identity in registration, status, heartbeat, ACK, WatchCommands and replica/fetch authorization must equal the leaf certificate Common Name. Fetch authorization checks ReplicaWorkerID because the replica sends that request. Reverse RPCs use the already-established session to that coordinator, not an unauthenticated new callback address. A peer cannot use the coordinator endpoint's method table to invoke worker-only methods.

With no TLS settings, the local-development transport remains plaintext and is not authenticated. This WIP does not claim HTTP authentication, RBAC, data-plane TLS or checkpoint-replica TLS; those remain WIP-17's separate security surfaces. TLS utilities alone are not evidence of runtime RPC security: see the real mTLS registration test in the acceptance record.
